# research-agent / wheel-discovery

> 职责：规定 research-agent / wheel-discovery 能力边界。
> 真源：对应子代理能力的输入契约、判定核心、产物格式和本能力输出字段
> 读取：维护读取

为主代理准备新写的工具、模块或组件查找现成方案，输出一张固定对比表，「自己写」作为基线一行，并给出推荐与决策摘要。

## §1. 输入契约与开工条件

从 `task_package.extensions.capability_contract.wheel_discovery` 读取：

- `target`：要做的工具、模块或组件及其用途。
- `requirements`：已锁范围内的需求条目，每条以 id 开头；对比表「能力覆盖」列逐条对照。
- `user_constraints`：用户已知的坑、偏好与红线；空列表表示用户没有补充。
- `known_candidates`：已知候选；全部纳入对比，其余候选自行发现。

`scope.read` 是仓内读面，用于核对接入代价：依赖清单、运行面、目录结构和现有验证命令。

BLOCK IF: `target` 或 `requirements` 为空，或任务没有可用的联网授权与 `research_search` / `research_fetch`。出口：返回 `needs_owner`，只点名缺失项。

工具面由 worker 按任务包收窄为研究工具与本地读写工具。用 `research_search` 找候选，用 `research_fetch` 读取发布页、许可证和候选仓库的原始源码文件；用读取类工具查看 `scope.read` 内的现状。需要安装或运行才能判断的点写进「待实测」列，由主代理另派实测。

## §2. 调研流程

1. **定对照项**：把 `requirements` 逐条作为能力覆盖的对照项，把 `user_constraints` 作为筛选条件。
2. **发现候选**：先纳入 `known_candidates`，再从包仓库、官方文档、GitHub 与社区讨论中找同类组件。按需求覆盖和红线初筛，保留有实际选择价值的候选；初筛淘汰的候选在「引用清单」末尾各附一行淘汰理由。
3. **核许可与维护**：记录许可证、最近发布日期和维护活跃度（近期提交、issue 响应），均引用抓取到的原文。
4. **核源码**：对声称覆盖关键需求的候选，读实现文件确认能力存在，记录读过的文件位置与结论。
5. **算接入代价**：对照 `scope.read` 中的现状，写出依赖、运行面、目录和验证命令各自的变化。
6. **写基线**：「自己写」按同样的列估计需要实现的部分、依赖变化和验证方式。
7. **给推荐**：选出推荐行并写明理由。命中红线的候选不作为推荐；证据不足以区分两行时，把该取舍写进 `owner_decisions`。

## §3. 对比表口径

| 列 | 填写内容 |
| --- | --- |
| 候选 | 名称与版本；基线行写「自己写」 |
| 许可与维护 | 许可证、最近发布日期、维护活跃度 |
| 能力覆盖 | 按 `requirements` 的 id 逐条标 `覆盖` / `部分` / `不覆盖` / `未核实` |
| 适配缺口 | 需要自己补的部分；与 `user_constraints` 的冲突写在这里 |
| 接入代价 | 依赖、运行面、目录、验证命令的变化 |
| 源码核查 | 读过的源码位置（URL 或路径）与结论；未读源码写 `未核查` |
| 待实测 | 需要安装或运行才能关闭的缺口：要验证什么、最小示例、判定标准；没有写 `—` |

「能力覆盖」标 `覆盖` 或 `部分` 需要源码或官方文档证据；只有 README 宣传或第三方陈述时标 `未核实`。
