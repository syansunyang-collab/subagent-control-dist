# 决策账本

> 职责：规定对齐三道共用的决策分类、记录门槛、呈现与执行期回报。
> 真源：必问 topic 闭集、默认项记录门槛、操作与决策的分界、呈现规则、执行期回报、流程裁量边界
> 读取：命中读取

每个待定点带一个 `topic`，topic 决定它是必问项还是默认项。条目字段、来源类型闭集与校验错误码以 `python -B ops/tools/alignment_recorder.py --schema` 为准。

## 1. topic 闭集

| topic | 含义 | 类别 |
| --- | --- | --- |
| `goal_scope` | 目标、范围、不做什么 | 必问 |
| `acceptance` | 什么算完成、怎么验、失败怎么办 | 必问 |
| `tech_route` | 新依赖、新组件、新 runtime、自写还是用轮子 | 必问 |
| `design_point` | 架构、数据流、进程或并发模型、持久化、对现有模块的改法 | 必问 |
| `user_visible` | 界面或输出形态、入口、主路径 | 必问 |
| `conflict` | 与用户说过的话或已锁定内容冲突 | 必问 |
| `layout` | 目录落点；按 `ops/protocols/repository-structure.md` §9 确定，规范留有选择时才考虑记录 | 默认项 |
| `parameter` | 方案内参数取值 | 默认项 |
| `naming` | 命名 | 默认项 |
| `internal` | 模块内部结构、标识符、测试组织、日志格式等实现细节 | 默认项 |

`design_point` 命中下列任一即成立：

- 架构变更：改变组件间调用或数据流拓扑（新增或移除层、服务、进程边界）；改变持久化形态或真源位置；改变并发、调度或通信模型；影响架构的模块拆分。
- 新增长期维护面：交付后需要周期性人工动作（升级、续期、清理、值守）；新增需跟踪上游变化的外部依赖；新增卸载或回滚时必须处置的持久资产。

一个决策同时落在两个 topic 时按必问归类。必问项由用户或领域负责人拍板，主代理给推荐与理由。方案内的参数问题不替代该方案本身的 `tech_route` 或 `design_point` 确认：问超时值之前，先问要不要引入这个组件。

## 2. 默认项记录门槛

默认项改变了下列任一内容时记入账本，并写推翻代价（`override_cost`）：

- 已确认内容之外的对外约定；
- 用户可见行为；
- 其他模块或任务需要遵循的约束。

对外约定的典型情况：模块外调用的接口与参数、被其他模块或外部程序读写的文件与数据格式（含被外部采集的日志格式）、配置键、模块外可见的名称。清单不封闭，兜底判据是是否形成其他模块或任务需要遵循的约束。

仅影响局部实现、撤销时无需调整上述约定或依赖的默认项不记录，也不进执行回执。改动接触接口所在文件不等于改变对外约定：重构函数内部、调整测试组织，约定与依赖不变的不记；改变外部依赖的行为，改动再小也记。是否比较过多个选项不作为条件；同一 topic 的默认项分别判断。

## 3. 操作不是决策

删除、覆盖、联网、安装、耗时验证属于操作：直接执行，记入交付报告末尾的操作清单（`ops/workflows/alignment/WORKFLOW.md` §9）；操作不进决策账本。

- 删除前能备份就先备份；git 可回退视为已备份；无法备份的删除在操作清单标「不可回退」。
- 把新依赖引入产品属于 `tech_route`；为实测在本机安装属于操作。
- 目录落点按 `ops/protocols/repository-structure.md` §9 直接确定，不单独提问。

## 4. 呈现

任何决策在锁定前呈现给用户；直接做道与执行期的默认项在交付报告里呈现。已确认的内容直接复用，不重问。

模式默认 popup；用户说「卡片」时切换 card；提问工具不可用时用 conversation，在对话中确认。

| 模式 | 呈现方式 | 批量接受 |
| --- | --- | --- |
| popup | 每个必问项、preview、marker 单独成题，推荐项排第一；每屏至多 4 题，按主题分屏，屏数不设上限 | 每屏末题「其余全部按推荐」，说明中列出它覆盖的默认项；不覆盖必问项 |
| card | 卡上分「要你拍板」「我替你定了」两节；必问项在前一节逐条列选项与推荐，默认项在后一节带推翻代价 | 用户回复「整卡按推荐」覆盖卡上单列的全部项目，含必问项，marker 除外；也可按编号修改 |
| conversation | 在对话中发卡片文本，结构同 card | 「整卡按推荐」只覆盖默认项；必问项、preview、marker 逐项作答 |

标准规格道的分屏与卡片文本由 recorder 从草案渲染（`ops/workflows/alignment/WORKFLOW.md` §3）；任务卡与直接做道由主代理按本表组织。

写草案：

- 每题只拍一个判断；选项说明写清与其他选项的差异和选后影响；推荐项附理由，默认项附推翻代价。
- 泛问改写成具体取舍：把「要不要优化」写成「列表页首屏加载目标定为 1 秒还是 3 秒」这类会改变范围、产物或验收的选择。
- 同主题的项目在草案中相邻排列；将尚未披露的默认项与推翻代价放进本次拍板材料。
- 在 S1 采访中询问用户已知的坑、偏好和红线（marker `user_constraints`），复用已给的约束。回答写入查轮子与成本挑战的输入约束。
- 一次确认只支撑该轮实际展示过的项目；未展示或未作答的项目保持待答，默认项也不假定接受。

## 5. 执行期回报

- planner 与 executor 遇到必问 topic 时返回 `needs_owner`，不自行决定；其余偏离规格的决定写进回执 `off_spec_decisions[]`（`topic / decision / reason`），只收必问 topic 与满足 §2 门槛的默认项。
- 回执因必问 topic 返回 `needs_owner` 时，标准规格道按 `ops/workflows/alignment/exit.md` §2 开轮问用户；任务卡道改卡后重新确认。
- 回执中的默认项在收口时进入交付报告（`ops/workflows/alignment/WORKFLOW.md` §9 第 2 项）。

## 6. 流程裁量边界

流程裁量在对齐中只覆盖编排：

| 可裁量 | 不在裁量内 |
| --- | --- |
| 审查派发次数、弹窗合并与分屏、事实侦察自查或委派 | 必问项、验收对象、`open_questions` 清零、非 PASS 审查的裁决 |

每次裁剪写进交付报告的流程裁剪一节。
