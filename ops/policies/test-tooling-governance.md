# 测试工具和脚本治理

> 职责：规定测试脚本和验收主体治理。
> 真源：测试资产分类、脚本准入和验收责任主体规则
> 读取：命中读取

本文件规定测试代码、运行证据、长期脚本资产和主体明确验收的落盘规则。它只管脚本和验证资产治理，不替代 `ops/protocols/repository-structure.md` 的目录归属，也不替代 verify-agent 的验收结论。

## 1. 资产分类

| 类别 | 路径 | 进入条件 | 提交策略 |
| --- | --- | --- | --- |
| 长期测试代码 | `tests/` | 验证对象、输入、断言和通过条件稳定，可由项目测试入口重复运行 | 提交 |
| 测试基线 | `test-baselines/` | golden、snapshot、benchmark 或领域参考样例稳定，并有更新规则 | 选择性提交 |
| 单次运行证据 | `test-results/` | 截图、日志、命令输出索引、浏览器状态、渲染图、导出表或一次性运行结果 | 默认只提交索引和模板 |
| cockpit 运行工具 | `ops/tools/` | 服务 cockpit 运行卫生、账本检查、派发构包、地图生成或证据索引 | 提交 |
| 项目维护脚本 | `scripts/` | 可重复执行的检查、安装、维护、导出或迁移入口 | 提交 |
| 验收报告 | `notes/verify/` | verify-agent 或 plan-checker 的审查结论和证据索引 | 选择性提交 |
| 临时实验 | `sandbox/` / `tmp/` | 一次性探索、试跑、草稿命令或可删除中间物 | 默认不提交 |

`test-results/` 中 2026-09-13 及以前已跟踪的运行证据被决策记录与 notes 引用，保留原位；此后的运行证据按上表只提交索引和模板。

`test-results/` 中的文件只证明本轮运行发生过。它们不能自动成为长期测试、工具或脚本资产。

## 2. 脚本准入

同时满足以下条件，才允许新增长期测试、工具或脚本：

- 验证对象稳定：输入、输出、退出码、断言或通过条件明确。
- 问题可机械判定：执行结果能由命令返回值、文件差异、结构化输出、截图索引或稳定断言判定。
- 路径已授权：目标路径在当前任务包 `scope.write` 内，并符合 `ops/protocols/repository-structure.md`。
- 失败行为明确：失败时返回非零、写出错误摘要或输出明确失败证据，不静默降级。
- 复用收益明确：覆盖可观察的功能行为或接口约束；运行次数、用例数和全绿结果不单独构成收益。
- 维护边界明确：写清入口、依赖、输入、输出、清理方式和维护责任。

配置驱动的功能使用独立夹具验证读写、选择和生效行为。真实配置与输出的接线检查从配置读取期望值，不在测试中抄写当前模型、档位、路径、候选数量或默认偏好。已有行为覆盖时复用；没有行为覆盖的自比断言、一次性计划表锁定和重复用例直接删除，不补替代测试。

接口、路径或默认行为变更的回归沿本次被改变的调用关系验证到直接消费者。夹具保留能暴露旧错误的差异，例如来源不同、旧副本存在或声明默认值省略；预期结果来自任务要求和已知反例，不从被测结果自身推导。已有真实解析器、校验器或加载入口时直接调用，避免另写一个更宽松的替代判据。已复现缺陷的失败输入与验证结果记入修复证据。失败输入及对应断言仍服务有效功能或接口契约时，复用已有覆盖，或按本节准入条件保留为回归用例。修复后复用未受影响的有效结果。

将仅服务一次迁移或排查的对拍、探针与长期回归用例分开。在创建临时资产的任务或记录中写明用途和退场条件；条件满足后，由有删除授权的维护者清理已无使用方的临时部分，并在原记录中记下处置。仍服务有效契约的部分按长期资产准入条件保留；删除授权缺口交对应 owner 处理。

任一准入条件不满足时，不新增长期脚本；当前任务需要的判断由执行者依据已有证据完成。

### 2.1 源码规模

`ops/tools/**` 与 `adapters/**` 的源码按职责拆分，单文件保持在 1500 行以内，单函数保持在 150 行以内。改动已超限的文件时，新增职责放进独立模块，不再并入超限文件；超限文件与函数排入 `ROADMAP.md` 延后事项，逐个拆分。拆分只搬移代码：函数体与对外接口不变，拆分前后运行同一组测试，并逐个比对函数体。`python -B ops/tools/toolchain_check.py` 列出超限项作为提示，不计入失败。

## 3. 禁止脚本化对象

以下对象不得用脚本替代判断：

- 需求颗粒度、需求歧义、规格锁定面是否足够。
- 提示词、文档、规则、灰区说明和验收语义是否清楚。
- 任何语义审核，包括规则质量门、删除测试、单指向测试、软化词是否被收束和失败出口是否足够。
- 防御性表达、空话、免责声明、责任转移和无信息重复。
- 用户是否接受方向、风险、体验、视觉手感或产品取舍。
- 领域语义是否等价，除非已存在稳定参考输入、参考输出和可机械比较的指标。
- 只有一次性探索价值的命令流水。

这些对象必须进入对应主体的审查或确认流程；主体闭集以 §4 为准。

## 4. 主体明确验收

禁止使用“人工核对”“人工验收”“人工检查”“人类检查点”“人工流程”等无主体表述。

需要任务外主体参与时，必须写成下列之一：

| 表述 | 使用场景 |
| --- | --- |
| 用户确认 | 方向、风险、效果满意度、是否继续、是否接受取舍 |
| 领域负责人确认 | MATLAB 参考语义、算法定义、业务指标、行业口径或专门领域判断 |
| 主代理证据审查 | 主代理读取已存在证据、回执、产物和报告后判断是否能推进 |
| verify-agent 验收审查 | 按 P7 选出的验收能力审查代码、功能、UI、规则结构或提示词污染 |
| 真实交互验收 | 打开真实界面、走真实用户路径、覆盖状态和截图证据 |

不需要任务外主体参与时，必须写明由主代理、子代理或具体 verify 能力执行哪类证据审查。

主代理先把用户目标转为可观察的成功与失败条件，再选择检查。交付结论对应实际调用方、入口、配置来源或执行画像及其消费结果；发布检查、预览、任务完成和独立审查的结论各限于已验证范围。已有证据对应的行为未被后续修改影响时可复用；影响结论的缺口补齐后再收口，不以通过数量或“未发现问题”推定未覆盖目标也完成。

## 5. planning 规则

PLAN 需要新增测试、工具、目录、脚本或验证手段时，必须在 `resource_delta` 写清：

- 资产类别：长期测试代码、测试基线、cockpit 运行工具、项目维护脚本或单次运行证据。
- 落盘路径。
- 服务的用户需要、规格 ID 或验证对象。
- 被哪些 task 使用。
- 输入、输出和失败行为。
- 维护责任和清理办法。
- 是否需要用户确认或领域负责人确认。

`test-results/` 只承载单次运行证据。PLAN 不得把 `test-results/` 写成长期能力、长期脚本或业务交付物。

## 6. verify-agent 边界

`verify-agent / code-verification` 可以在任务包授权范围内写或修改测试代码，并运行测试。测试必须绑定当前任务目标，不能只证明命令跑过。

`verify-agent / functional-inspection` 可以运行入口、打开产物、保存截图、导出表和命令输出索引。写入目标只限报告、handoff、progress 和 `test-results/functional-inspection/<package_id>/`。

`verify-agent / ui-interaction-inspection` 可以打开真实 UI、走用户路径、保存截图、录屏索引、浏览器状态和渲染图。写入目标只限报告、handoff、progress 和 `test-results/ui-interaction-inspection/<package_id>/`。

`verify-agent / anti-defensive-inspection` 只审语义、代码表达、提示词、说明和脚本策略中的防御性兜法。它不写脚本、不运行探针、不生成测试工具。

`verify-agent / prompt-bloat-inspection` 只审规则膨胀、重复、受众错配和上下文污染。它不写脚本、不生成测试工具。

`semantic-review-agent / rule-quality-inspection` 只用模型语义判断审查规则质量门。它不写脚本、不运行脚本、不生成测试工具、不用代码或机械扫描替代语义结论。

静态终验可消费 `review_evidence.mjs` 在派发前生成的机械事实；verify 的封闭卷宗（`evidence_only_v1`）不授权 reviewer 运行脚本，semantic review 可按完整索引使用只读工具。机械事实不替代上述业务 gate。

## 7. 证据提升规则

单次运行证据需要提升为长期资产时，必须另有明确任务，且同时满足：

- 本轮证据已经证明该检查有复用价值。
- 输入、输出、通过条件和失败行为已稳定。
- 目标落盘路径属于 `tests/`、`test-baselines/`、`ops/tools/` 或 `scripts/`。
- 后续维护责任明确。
- 提升后的资产不依赖本轮临时目录、临时端口、临时账号或临时路径。

没有提升任务时，`test-results/` 保持单次运行证据，不进入长期资产。

## 8. 验收

按本次改动选择检查，并记录检查对象、方法、结果和未覆盖部分。复用仍然有效的证据。

修改验收责任表述时，核对具体主体和动作；修改 anti-defensive-inspection 的能力边界时，核对其授权与本文件§6一致；修改可复用模板时，核对受影响的消费副本；检查差异格式时使用 `git diff --check`。定向扫描只用于定位文字，规则含义由执行者结合上下文判断。
