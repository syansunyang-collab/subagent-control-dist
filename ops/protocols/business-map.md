# business-map.md

> 职责：规定业务能力地图的建立、维护和验收。
> 真源：业务能力地图路径、输入来源、结构字段、创建流程和验收规则
> 读取：命中读取

业务地图记录项目业务能力，不记录 Codex 编排治理文件。编排地图和业务地图分开维护：编排地图定位代理、workflow、policy、route、prompt 和编排型 skill；业务地图定位真实业务目标、能力边界、证据来源、实现入口和验证入口。

## 1. 地图分工

| 地图 | 路径 | 维护方式 | 内容边界 |
| --- | --- | --- | --- |
| 编排地图 | `ops/map/cockpit-overview.md` | `ops/tools/cockpit_map.py` 自动生成 | Codex 编排治理文件和 `layer=orchestration` 的 skill |
| 业务地图 | `map/business-capability-map.md` | 主代理按本协议维护 | 业务能力、业务证据、实现入口、验证入口和未确认缺口 |

`map/business-capability-map.md` 是业务地图唯一入口。`ops/map/` 保持编排地图专用，`ops/tools/cockpit_map.py` 只扫描和生成编排地图。

## 2. 创建触发

WHEN: 用户给出真实业务目标，或仓内已有业务代码、业务文档、数据样例、业务流程、测试入口会影响执行计划。

ACTOR: 主代理

MUST:

1. 先界定业务地图输入来源：`PROJECT.md`、`STATUS.md`、`ROADMAP.md`、已确认的 `docs/`、`design/`、`src/`、`tests/`、`data/`、`outputs/` 和用户点名材料。
2. 以业务能力归类，不以目录树、文件名或工具名归类。业务能力必须回答：服务什么业务目的、输入是什么、输出是什么、证据在哪、实现或文档入口在哪、如何验证。
3. 没有证据的条目进入待确认缺口，状态保持 `candidate` 或 `blocked`。
4. `notes/`、handoff、扫描报告和运行输出只作为证据线索；主代理确认稳定后，才能把结论写入业务地图。
5. 首次创建 `map/` 时，同步更新 `PROJECT.md` 的目录约定。

BLOCK IF: 业务地图条目没有证据路径；把 `ops/` 编排治理文件当业务能力；从文件名或目录名直接推断业务能力；业务地图落入 `ops/map/`。出口：降级为待确认缺口，补证据后重试；补不了则收口 `needs_owner`。

## 3. 结构字段

业务地图使用下列固定结构：

1. 建图状态：记录地图状态、更新时间和当前证据边界。
2. 项目业务边界：记录本仓做什么、不做什么、输入输出边界和业务受众。
3. 能力总览：用表格列出能力 ID、名称、业务目的、证据、实现或文档入口、验证入口和状态。
4. 能力关系：存在两个以上已确认能力时，补能力依赖或数据流关系。
5. 能力详情：每个已确认能力记录输入、输出、边界、关键文件和验证方式。
6. 待确认缺口：记录缺少业务事实、证据不足或等待 owner 裁决的事项。

能力状态闭集：

| 状态 | 含义 |
| --- | --- |
| `confirmed` | 已有证据路径、入口和验证方式 |
| `candidate` | 有证据线索，但能力边界或验证入口未闭合 |
| `blocked` | 需要 owner、外部材料或工具环境补齐 |
| `retired` | 曾经存在但已明确退出当前业务地图 |

## 4. 维护规则

- 业务能力边界、输入输出、验证入口或项目业务范围变化时，更新业务地图。
- 普通文件移动、临时扫描、运行日志和子代理回执不直接触发业务地图更新。
- 实现细节稳定后进入 `docs/modules/` 或 `docs/architecture/`；业务地图只保留入口和能力关系，不复制长篇实现说明。
- 业务地图中的路径使用仓库相对路径；本机绝对路径、密钥、运行态缓存和未脱敏生产数据留在地图之外。

## 5. 验收

创建或修改业务地图后执行：

```powershell
Test-Path map/business-capability-map.md
```
