# 收割核验与审计收口

> 职责：规定回执核验步骤、批次回滚、互补审计视角和常见事故对照。
> 真源：本文件
> 读取：命中读取

## 回执核验

本节逐片核验适用于普通执行和无 Acceptance Contract 的审计。合同编译的验收叶子不逐片裁决，其 reducer report 按 `ops/workflows/planning/validation-dispatch.md` 消费。

结合实际改动和已有证据消费回执，按任务目标作出判断。已有有效验证结果直接复用；证据存在具体缺口时，只核对该缺口对应的修改。提交信息与实际改动、证据保持一致。

BLOCK IF: 文件集不一致、清单外写入或改动与回执不符。出口：核实差异并修正；无法解决时说明缺口并收 `needs_owner`。

批量作业的核验节奏：先完成先核验，不攒到全部终态再统一处理——早发现的切片级问题能在下一波派发前修正切法。

完成通知的内部收割与阶段发现交付分别安排。普通探索的阶段交付方法见 `ops/skills/subagent-fleet-discipline/references/reducer-wave.md` 的「阶段消费」。

## 批次回滚

回滚按批次粒度处理：先冻结当前工作区并记录 `git status --short`，只回滚该批 `write_scope` 内的文件；清单外临时物先隔离，确认不属于其他批次产物后再清理。多个批次同时异常时按依赖反序处理，下游先停，避免把上游证据抹掉。

## 审计收口

已有证据能够判断修改结果时直接收口。尚有具体问题需要独立判断时，选择对应视角审查本次修改；视角用于定位问题，不构成固定审计批次：

| 视角 | 查什么 |
| --- | --- |
| 漏网 | 本次明确要求的修改是否遗漏 |
| 误删 | 改过头的；被删语义是否有承载方，契约面是否被碰，约束是否漂移 |
| 言行对账 | 提交信息、报告声称与实际 diff 逐条核 |
| 实弹 | 有可运行链路时，在隔离副本或安全夹具里跑关键场景 |

按待解决的问题确定审查范围，只覆盖本次修改。报告说明实际检查内容与未解决问题。语义审查材料由 `ops/protocols/subagent-information-injection.md` 的 `semantic_review_v2` 承载。

无 Acceptance Contract 的临时审计由主代理逐条裁决。合同编译审计的裁决与 loop 动作只看 `ops/workflows/planning/validation-dispatch.md`，不适用本节逐片收割。两名审计员独立命中同一问题时提高证据权重，不自动扩大严重度。

## 常见事故对照

| 事故 | 根因 | 处理 |
| --- | --- | --- |
| 提交信息声称的改动磁盘上不存在 | 未核对实际产物 | 核对该改动与对应证据 |
| 两个代理互相覆盖同一文件 | 分组没按文件切 | 重新切批；共享文件串行 |
| 子代理顺手破坏字段契约 | 任务包缺必留清单 | 补必留清单并重派或手工修 |
| 审计结论与用户看到的结果不符 | 证据未覆盖实际问题 | 定位差异，只检查该问题对应的修改 |
| 临时物被吞进提交 | 收工没看 status 就全量暂存 | 逐文件暂存，只提交本任务文件 |
| 十个切片九个空等一个 | 攒批收割 | 先完成先收；只对本 run 已知 task id 调 `subagent_get`，无终态就干别的 |
| 全批用收口档角色烧穿预算 | 未按判断量分档 | 按 parallel-slicing 的分档表重选角色 |
