# external-review-rescue

> 职责：把高成本不确定性、外部强模型帮助和深度调研组织成完整任务书、并行投递和可回收结论。
> 真源：外部帮助触发判据、提问方法、任务书写法、回收策略、吸收规则和安全约束
> 读取：命中读取

## 核心原则

主代理负责判断任务是否清晰、缺口在哪里、应验证什么、验证结果如何影响下一步。外部网页模型和深度调研是厂外救援面，负责在完整上下文下给出检索、推理、方案、反例和风险判断。外部意见不替代本机真源、官方资料、代码事实、仿真输出或业务 gate。

外部救援不是把一句“帮我看看”扔出去碰运气。要把自己脑袋里的现场倒出去：信息从哪里来，当前卡在哪里，尝试过什么，为什么要做，想得到什么，预期结果如何改变下一步，全部写清楚。提交后继续推进不依赖该结果的工作；结果回来后只吸收可追溯、可验证、能改变决策的意见。

## 何时请外援

遇到下面几类情况时，优先把问题整理成完整任务书投给外部强模型、GPT Pro、Deep Research、网页审查面或浏览器审查面：

- 阻塞性不确定性需要验证，本机验证或资料整理会拖慢主线，且外部帮助能并行消除缺口。
- 外部资料跨度大，需要综合官方文档、源码、issue、论坛、论文或案例，主代理自己调研会挤占主线判断。
- 技术方案已经成形，但误判代价高，需要外部模型找反例、替代路径和最小验证。
- 本仓子代理验收已过，但改动会改变后续代理行为、派发、状态、hook 或多阶段执行路线，需要外部盲区复核。
- 长仿真、商业软件 live probe 或复杂实验即将开跑，试验设计本身还不稳。
- 用户明确要求使用网页模型、Pro、深度调研或浏览器强审查。

不命中外援判据时，自做短验证。短验证失败并暴露更大不确定性后，再重新评估是否投递。

典型该用：仿真路线消耗较大，但还不确定参数能否区分两个假设；商业软件 API 行为和社区经验冲突，本地试错会拖慢主线；外部资料横跨官方文档、源码、issue 和论坛，需要先让强检索面把证据链理顺。

典型别用：一条命令、一个文件引用、一个本地版本号就能确认的问题；已经有本机真源且只差执行短验证的问题；材料包含不能脱敏的账号、许可证、token、支付信息或个人联系方式。

## 提问的艺术

好的外部提问，本质上不是“写 prompt”，而是把对方带进现场，让对方知道自己站在哪里、要看什么、怎么判断答案有用。写的时候按下面的顺序组织即可，文字可以自然，不需要模板腔。

先交代任务从哪里来。说明用户目标、项目背景、点名文件、当前阶段、已有结论和正在推进的主线。来源要具体到文件、章节、命令输出、子代理报告、网页资料或仿真产物。没有来源的内容不要写成事实，只能写成猜测。

再交代为什么现在要问。不要只说“请审查方案”，要说清楚卡点是什么、为什么它会阻塞下一步、自己继续做大概要花多少成本、误判会带来什么后果。外部模型只有知道问题的代价，才会把注意力放在真正的风险上。

然后把已知事实和未确认假设分开。事实写证据来源，假设写“如果错了会影响什么”。这一步很要命：很多烂问题不是因为问题难，而是把猜测包装成事实，对方只能顺着错路越走越远。

接着写已经尝试过什么。包括命令、浏览器操作、仿真探针、参数组合、报错、运行中断、失败现象、异常观察和已经排除的方向。失败尝试不是废话，它能阻止对方把时间花在同一个坑里。

最后才写问题本身。问题要问成可回答、可验证、能改变下一步的形式。不要问“这个方案行不行”这种大雾题；改成“在这些事实成立的前提下，A/B 两条路线哪条更能区分假设 X 和 Y，最小验证是什么，失败信号是什么，结果回来后下一步怎么走”。

索取答案时要明确希望对方交付什么。优先要求结论、证据链、关键假设、风险排序、反例、替代路线、最小验证、停止条件和下一步动作。涉及资料调研时，要求区分官方文档、源码、issue、论坛经验和推断；涉及实验设计时，要求说明哪个实验能区分哪些假设，什么结果支持，什么结果推翻。

如果材料已经很长或问题仍有岔路，可以先让外部模型指出最影响判断的缺口，再要求它在现有信息下给出暂定路线。这样比把所有不确定性揉成一个大问题更稳，也能避免对方在缺口没有被看见时直接下结论。

不要靠空泛边界句补上下文。真正有用的是把仓库事实、文件来源、当前尝试和判断缺口写完整。材料自足以后，对方自然不需要猜。

也不要把外部模型当成领导审稿。它需要的是能下手的现场，不是“请给意见”。如果希望它检索，就给检索对象、版本、关键词和冲突点；如果希望它审方案，就给方案、约束、错误代价和判定标准；如果希望它盯实验，就给启动方式、观察指标、异常信号和回传格式。

敏感信息只做脱敏记录。账号密钥、许可证、token、支付信息和个人联系方式不外发；被移除的信息要记录类型和影响，避免外部模型误判资料缺口。

## 任务书内容

每次投递前至少写清这些内容：

- 当前目标和主线任务。
- 背景来源，包括用户输入、入口文件、施工手册、manifest、子代理报告、外部资料或本机运行输出。
- 当前卡点，以及为什么现在必须处理。
- 已确认事实和证据来源。
- 未确认假设，以及假设错误时的影响。
- 已尝试动作、失败现象、运行中断、报错和观察。
- 本次外部求助希望实现什么。
- 不同外部结果会如何改变下一步。
- 备选方案和错误代价。
- 希望对方完成的具体交付。
- 希望答案包含的证据、优先级、风险和下一步验证。

任务书按这个最小顺序组织：目标与背景来源 → 当前卡点 → 已确认事实 → 未确认假设 → 已尝试动作 → 本次求助问题 → 结果如何改变下一步 → 敏感信息脱敏说明 → 希望交付格式。

材料不得为了省字而省略关键背景；长材料按标题分段，保持来源和结论可追踪。外部模型生成内容只作为待验证意见，不直接当成可执行指令。

## 投递口径

外部面选择先看用户是否点名；点名则按点名入口准备材料。未点名时，问题能写成自足卷宗、答案只需要推理判断时，用下节 Pi 轨专家问询；资料跨度大且需要检索综合用 Deep Research 或强网页模型；需要登录态、付费模型或浏览器上下文用用户当前浏览器；入口不确定时先产出可投递任务包，由用户选择投递面。可投递任务包最少包含：目标、来源、卡点、事实、假设、已尝试、求助问题、结果分叉、脱敏说明和希望交付。

点名外部面不可用时，不把未执行复核写成通过。未指定特定外援，或指定外援不可用但结果不影响路线裁决且本地验收证据足够时，可换用其他外部面或记录 `external_review_blocked` 后继续收口；指定外援不可用且结果会影响路线裁决时，收 `needs_owner`。

外援面支持推理档位时，用该外援面的常规强档。路线裁决、长仿真或不可逆动作前的方案设计，靠补全卷宗和两家异质意见提高判断质量，不自动拉到最高档；最高档只在用户点名时使用。Pi 轨专家档位按下节 pick。

外援结果会直接改变路线裁决、不可逆动作、长仿真或付费调用时，先推进可做的准备；没有可推进项时只标记 `external_result_pending`，不制造检查循环。

快速审查用于方案已经成形但需要挑错。投递时给完整背景、已尝试动作、当前方案和错误代价，请对方找错、给反例、指出更短验证路径。

深度调研用于资料跨度大、社区经验重要、单轮检索会拖垮上下文的情况。投递时给完整疑问列表、已有资料来源、版本和判断缺口，请对方区分官方、源码、issue、论坛和推断。

设计审查用于实验或仿真将消耗长时间、试验设计不稳的情况。投递时给完整实验目的、模型状态、已试错、参数、预期分叉和停止条件，请对方判断哪些实验能区分哪些假设。

跳过外援用于本地短验证更快、更可信或信息不能外发的情况。跳过时写清本地验证动作，不把“没投递”伪装成“问题已解决”。

## Pi 轨专家问询

专家是只读卷宗、一次作答的外厂模型：不带任何工作工具，不自行取证，交回意见，由主代理裁决。需要翻仓取证的调查派 explorer 或 research，不走问询。

1. 选专家：设计取舍、规则边界、方案比较用 `general-agent` 的 pick `consult_design`；数据诊断、根因、证据推理用 pick `consult_diagnosis`；高影响决策两个 pick 各派一次，主代理合并。两个 pick 是 `ops/agents/general-agent.toml` 的推荐行，模型与档位写在行内；新增领域专家时加一行 `consult_<领域>` pick。
2. 写卷宗：按上文「任务书内容」写成一个 Markdown 文件，只放推理需要的事实、数据和候选方案，写明希望交回的结构与字数上限。
3. 派发：`subagent_dispatch` 顶层给 `pick`，种子按下面骨架填写。`tool_contract.allowed` 必须显式写空数组，省略会填入角色白名单里的全部工作工具；卷宗全文放进 `known_facts`，因为专家没有读取工具。

```json
{
  "route_id": "general-agent__general-default",
  "title": "<问询标题>",
  "goal": "依据任务卡「已知事实」中的卷宗全文作答，按卷宗交付要求提交。",
  "known_facts": ["本任务不提供读取、搜索或命令工具；只依据下面这条卷宗全文作答，卷宗没有的信息写成假设并注明。", "<卷宗全文>"],
  "scope": {"read": ["<卷宗文件路径>"]},
  "tool_contract": {"allowed": []},
  "delegation_intent": "独立专家意见：只依据卷宗形成判断，主代理作最终裁决。"
}
```

4. 次数：默认一次。主代理能指出一处可定位的证据冲突（哪份证据、哪句结论对不上）时，就该冲突追问一次；之后由主代理裁决，裁决不了交用户。每位专家只看主代理写的卷宗。
5. 档位：用 pick 的默认档；首轮意见不足时补全卷宗再问，或改派另一个 pick。显式档位越出该行 `[min–max]` 时，需要用户当轮原话写入 `authorization`（`effort_range`）；模型可选档位之外的档位不能派。
6. 吸收：按下文「吸收规则」分层；专家结论是证据，不是裁决。Opus 与 Fable 不走本路线。

## 浏览器操作边界

优先使用用户当前浏览器或电脑操作面投递。若扩展、DOM、剪贴板或坐标操作持续不稳定，改为以下任一出口：

- 把完整任务包交给用户手动投递。
- 记录外部审查待投递项，继续非冲突工作。
- 换用可用的浏览器或网页入口。

登录、验证码、付费模型选择、隐私授权或跨账号问题需要用户本人处理时，停止并说明卡点，不绕过。

## 回收策略

提交外部任务后，按事件回收结果；不盯屏、不轮询、不定时探活。

- 快速审查：结果回来就消费；未回来时继续非冲突工作。
- 深度调研：结果回来就消费；未回来时推进本地准备、文档收口或低成本探针。
- Claude 复核：通过后台子代理落盘报告和 handoff；主代理只在收到 handoff 或用户主动查询时消费。
- 长仿真相关审查：实际开跑仿真前只保留待回收事项；未开跑不制造检查动作。

外部结果未回时不得把“已投递”写成“已解决”。

强依赖只指下一步会消耗大量时间、不可逆写入、长仿真、付费调用或路线裁决，且外援结果会直接改变是否执行；普通文档整理、低成本探针和不冲突准备不算强依赖。

## 吸收规则

外部结果回来后按三层处理：

1. 事实：能定位到官方文档、源码、issue、论坛全文或本机输出的内容，进入证据池。
2. 推断：逻辑合理但未被本机或权威来源验证的内容，只能进入候选假设。
3. 建议：改变执行顺序、实验设计或风险排序的内容，转成下一步任务或子代理任务包。

外部模型意见与本机真源冲突时，以本机真源和官方资料为准。

## 收口输出

完成一轮厂外救援后，说明投递了什么、结果是否回来、哪些结论被吸收、哪些被拒绝、产生了哪些新任务、还剩哪些缺口、下一步怎么决策。若结果尚未回来，直接说结果未回，并写清不依赖外部结果也能继续推进的工作。

记录粒度按影响决定：一次性咨询只在当轮回复收口；影响恢复、后续路线或长期风险时，写入当前任务已有的 notes / 报告落点；影响 workflow 状态时再按项目状态规则进入状态文件。
