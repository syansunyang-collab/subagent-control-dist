# 任务书模板

> 职责：提供规则语料清洗整修和审计任务书模板。
> 真源：规则语料清洗子任务任务书模板
> 读取：命中读取

> 用途：第 2 步整修与第 3 步审计的派发任务书骨架。`<>` 为填充位。派发纪律（分组、模型、回执核验）见 `ops/skills/subagent-fleet-discipline/SKILL.md`；本文件只管任务书内容。经本仓派发链构包时，模板整体填入 seed 的 `goal` 与 `contract` 自由字段、文件清单拆入 `scope.read` / `scope.write_extra`，批量构包命令形态见 `ops/skills/subagent-fleet-discipline/references/batch-dispatch-playbook.md`。

## §1 整修任务书模板

```
工作目录 <绝对路径>。不许提交，不许创建、删除或重命名文件，只许改整修对象清单内的文件。

任务：对以下文件做写作宪法合规整修。只改表达形态，不改规则语义；语义级问题记入回报，不动手。

第一步，通读判据（只读）：<宪法文件路径>，重点 §1 原则与对照样例。

整修对象（只许改这些）：
<文件清单，绝对路径逐行>

必修（命中即改）：
1. 括号反写：属性塞括号的改独立短句；并列枚举类括号保留。
2. 禁令堆：连串禁止句围着同一动作的，改祈使句直接给动作。
3. 软化词与未定义限定词：无判定条件的补条件或删；拿不准记 skipped。
4. 修辞、比喻、情绪词：改技术陈述。
5. 跨层冗余：复读其他文件真源的句子改一跳指针或删；跨文件双真源拿不准记 skipped。
6. 外域枚举：罗列"什么不归本文件管"的清单句，有通用收口覆盖时删。

必留（逐字不动，动了会破坏契约）：
1. <机器读取的块：schema、配置块、卡片>
2. <字段名、枚举值、值域>
3. <标题行与章节编号——外部锚点引用>
4. <文件头部约定行>
5. <其他本语料特有契约面>

验收（全部通过才收工）：
<机械验证命令清单；没有机械验证时写：全文引用抽查可解析，改动文件自读一遍无断句>
失败就修到过；某文件改不到通过就回滚该文件并记 skipped。

回报格式（最终消息只含三段）：
1. 每文件改动点：原则编号+一句改了什么；无改动写「无命中」。
2. skipped：语义级发现与拿不准的位置+原因；没有写「无」。
3. 验收：命令输出最后一行原文。
```

## §2 审计任务书 A：漏网视角

```
工作目录 <绝对路径>。只审查、只报告，不修改任何文件。

使命：对 <范围> 做一条不落的全文审计，找出仍违反写作宪法的句子。此前的整修和审核都漏过东西，默认还有漏网。

第一步，通读判据：<宪法路径> 与病灶指纹表（`ops/skills/rule-corpus-cleanup/references/fingerprints.md` 的 §1、§2，可整段拷进任务书）。

第二步，逐文件全文逐句过，判定框架每句五问：
1. 受众：这句的执行者是谁？拿着它有可执行动作吗？
2. 上层承载：这句的信息是否已有别的真源？
3. 删除测试：删掉这句，行为变不变？
4. 可判定性：触发谓词凭可观察事实判得动吗？
5. 形态：括号反写 / 禁令堆 / 软化词 / 修辞？

第三步，交报告前自问：哪个文件没读全？哪类病灶没查？补查后才交。

回报：
1. findings：file:line、判据编号、问题一句、修复方向一句；FAIL 级在前。
2. 覆盖表：每个被审文件一行「路径 | 全文已读 | findings 数」，不许缺行。
3. 边界声明：没审什么。
```

## §3 审计任务书 B：误删视角

```
工作目录 <绝对路径>。只审查、只报告，不修改任何文件。

使命：整修过程刚结束（范围 <基线提交>..HEAD）。反向找茬：有没有删掉真正有用的语义、改丢契约、或整修者声称改了但实际没改的地方。默认有问题，去证明。

逐项核查 diff 中每个被删或改写的句子：
1. 误删：被删句子的语义是否真由替代真源承载？打开那个文件确认，不凭注释相信。
2. 契约面：字段名、枚举值、标题、机器块在 diff 中是否被碰？碰过即 FAIL。
3. 语义漂移：禁令改祈使的改写中，新句约束范围与旧句是否等价？放宽或收窄逐条给出旧句/新句/差异。
4. 言行一致：每个提交信息的声称与实际 diff 逐条对账；声称改了但磁盘没改的逐条列出。

回报：findings（类型：误删/契约/漂移/言行不符）/ verified（核过无损的面）/ 边界声明。
```

## §4 审计任务书 C：实弹视角（可选，语料配有可运行工具链时用）

```
不信代码读出来的结论，用真实命令把关键链路跑一遍。在隔离副本（worktree 或目录拷贝）中：
- 构造最小夹具（伪造输入、状态文件、事件）。
- 真实执行工具链关键场景各一遍，记录命令与关键输出行作为证据。
- 任何与契约不符即 FAIL finding。
注意核对副本基点是否真含被审代码——基点挂错时先报 FAIL 再自行搭沙箱绕行。
```

## §5 裁决纪律

- findings 由主持者逐条裁决：采纳的修复并跑机械验证，搁置的写明理由入提交信息或收尾报告。
- 两名审计员独立命中同一问题的，优先级升一级。
- 审计员的报告同样不可尽信：FAIL 级 findings 修复前先亲自看一眼现场。
