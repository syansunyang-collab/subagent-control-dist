# 规则写作门

> 职责：规定控制面规则的写作原则、不合格判据和变更流程。
> 真源：规则写作原则、受众落位、R1–R12 不合格判据和规则变更流程
> 读取：命中读取

本文件是控制面规则和模型接口文案的写作真源。模型接口文案指直接指导模型选择、调用或处理工具结果的文字，包括源码中的description、参数说明、seed模板、错误提示和运行通知。普通实现、注释和面向人的UI文案不按模型规则审查。语义审查由 `semantic-review-agent / rule-quality-inspection` 使用本判据。

## AGENTS 专项方法

创建、维护或精简 `AGENTS.md` 时，按需使用 `ops/skills/rule-authoring/references/agents-authoring.md`，先核对宿主加载与受众，再确定高频内容及下沉位置。已有有效方法与取证直接复用，单行等义修补不额外展开专项调查。

## 模型指南适配

参考官方模型指南迁移或调校提示时，按需读取 `ops/skills/rule-authoring/references/model-guided-prompting.md`，核对型号、任务目标与读者，形成候选改动及对照验证。

## 0. 写作目标

规则的目的是塑形：教执行者把活干对，不是防执行者做错。每条规则落盘前先回答：它让哪个动作做对、做快或做齐了？答不出即负资产——只消耗读取预算、增加执行犹豫，不产出正确动作。体积不是目标而是症状指标：塑形密度高的文件自然短。

## 1. 写作原则

1. **唯一真源**：一个事实只维护一份定义，各消费面复用或生成对应投影。schema与参数说明各有用途且保持一致，不因出现两次判重复；独立维护相同事实或第二处没有新增帮助时才合并。同一文档对同一真源的指针合并到首处。
2. **删除测试**：规则必须改变至少一个执行行为（是否继续、派谁、读什么、输出什么、失败是否阻断、是否更新状态）。删除后一切不变的规则不写。
3. **单指向**：一条规则只指向一个主体、一个动作、一个触发条件。可两可的规则拆分或删除。
4. **增量门禁**：BLOCK IF 只写从 MUST 推不出来的新约束（新主体、新时机、新例外）。MUST 的逐字或逐义否定不写。
5. **出口必备**：每个 BLOCK / 禁止 / 阻断必须能从触发处直接定位到出口之一：修正后重试、收口 `needs_owner`、用户裁决、进入规则维护流程、显式降级。写不出出口的门不落盘。
6. **失败处理一句话**：缺什么补什么；补不了，`needs_owner` 并说明缺口。不维护穷举失败表；新失败模式出现时修流程，不加表行。
7. **先判必要性，再选机制**：先追踪删除拒发后的最坏实际副作用。若最坏仅为任务失败、回执说明并由主代理重派，就改为执行引导或可见结果，不设拒发门，也不把偏好转移进脚本。真实授权、输入形状、身份信封与资源边界的保护保留。必要且机械可查的约束交给 config、hook、sandbox、脚本或状态机；文字说明参数填法、机制位置、触发条件和失败出口，不重复执行检查。
8. **按需与边界**：读取、取证和工作粒度等可逆判断可使用“按需”等弹性表达，结合目标与已有上下文执行，不为消除模糊追加条件枚举或重复检查。授权、不可逆动作和阻断条件写清边界与出口；避免用未定义的模糊谓词触发硬后果。工作粒度词按 `ops/protocols/granularity-ladder.md` 用词。
9. **受众落位**：每段内容归属唯一受众——入口（`AGENTS.md`）只写高频触发和真源索引；protocol 写稳定字段和值域；policy 写低频判断和失败收口；workflow 写阶段状态机；capability 只写单角色可观察、可执行的本能力动作；设计背景和复盘进 docs / notes。写给子代理的内容必须是该角色本次任务内可观察、可执行的。
10. **只写推不出的**：规则只写两类内容——模型自己推不出的项目特定决策，和违反代价高到必须设门的红线。其余信任执行者常识，不写。
11. **指针约定**：跨文件引用深度 ≤1，任何文件到真源最多一跳；指针必须带一句话语义说明，不写裸指针；子代理可见材料（公共提示词、能力提示词、任务包）不写仓库指针，子代理需要的内容经任务包或 `required_files` 注入。
12. **祈使塑形**：行为塑形写祈使句自然语言——动词开头，直接给该做的动作（「先看地形再读正文」「同型任务一次批量派出」）。禁止句不用于塑形，只出现在门禁的 BLOCK IF 内。
13. **标签纪律**：治理条文的门禁与触发使用 WHEN / ACTOR / MUST / OUTPUT / BLOCK IF / STATE UPDATE，按需取用；行为引导使用自然语言。工具参数、错误和通知按各自接口槽位写短句，不套治理条文的标签格式。
14. **对照法**：好例承担塑形，写到可照做（动作、对象、顺序）；坏例只在好例单独存在会被误读时加，一句点出误读方向即止。坏例三不：不指名待废除的旧机制、不复述坏动作的可执行细节、不引入好例之外的新概念。好例在前，坏例条数不超过好例。
15. **文件自足**：读者凭本文件即可走完其职责的常规路径，不被迫中途打开第二个文件；跨域细节留一跳指针。边界：自家职责写全（自足），别家职责只指（一指）。
16. **技术语调**：陈述句技术风格；路径、字段、命令、数字写全写准；不用修辞、比喻和情绪词。准确优先于生动。
17. **格式规整**：统一头部（职责 / 真源 / 读取）；文件引用写 `ops/...` 全路径；闭集用表格；同类条目用同构句式。

对照样例：

| 原则 | 好 | 坏 |
| --- | --- | --- |
| §1.8 按需与边界 | 「按需补充原文或差异，复用已有有效内容。」 | 「每回合重新读取全部入口。」——把取证变成固定开销。 |
| §1.12 祈使塑形 | 「同型任务一次批量派出。」 | 「不得逐个派发；不得在批量可行时拆散。」——两句禁止围着一个该做的动作绕。 |
| §1.13 标签纪律 | 本文件 §3 变更流程：WHEN / ACTOR / MUST / OUTPUT / BLOCK IF / STATE UPDATE 各占一行。 | 把「此时必须重做，否则视为违例」藏进说明段落。 |
| §1.9 受众落位 | 能力提示词只写判定核心、专属字段和执行期可观察的守则。 | 能力提示词复读「接什么 / 不接什么」的准入枚举——路由判定归入口调度规则与 route 卡，子代理拿到包时路由已定。 |

### 模型接口落位

核对模型在调用时实际能看到的组合文本，不把仓库里存在一段说明等同于调用方已获得说明。

| 消费面 | 写入内容 |
| --- | --- |
| AGENTS | 项目约定、跨工具协调与业务裁决；不代写调用手册 |
| 工具description / 用途摘要 | 何时用、做什么、主要边界；摘要不再复述整份合同 |
| schema参数说明 / seed模板 | 填法、相邻概念区别、省略行为；目标声明与访问授权分开表达 |
| 返回结果 / 错误 | 实际结果、具体缺口及当前合法下一步，不暗示未验证成功 |
| 运行通知 | 本次状态下的下一步；已有消费记录或可用产物时据此分支 |

只在对应槽位写需要的信息，不要求每个工具重复全表。参数、默认值、权限和错误出口的文字承诺与实际实现一起核对；全局策略不只藏在可能尚未激活的单个工具里。

## 2. 不合格判据（R1–R12）

新规则命中任一 FAIL 不得落盘；存量规则命中时进入规则维护流程。判定单位是动作语义不是词面；豁免必须是写出来的字；「跑了没出事」不构成通过。

| # | 判据 | 级别 | 修复 |
| --- | --- | --- | --- |
| R1 | 自举悖论：解除某条 BLOCK 所必需的动作，被该条或同域另一条 BLOCK 禁止 | FAIL | 补豁免句 |
| R2 | 义务-禁止对撞：同一情境下一条 MUST 要求的动作命中一条 BLOCK（含两个未定义术语实指同一动作的变体） | FAIL | 合并术语，重写为单条 |
| R3 | 无出口门：BLOCK 触发后文内及被点名文件中不存在合法后继动作 | FAIL | 从 §1.5 出口闭集补 |
| R4 | 锁无释放：占有类规则（scope、授权、gate 占位）未显式列出释放事件集 | FAIL | 补释放事件清单，事件须对应既有机制 |
| R5 | 不可能义务：合规判定依赖不可观测或跨上下文压缩不可持久化的状态（如「已做过则再做即违例」） | FAIL | 删（若被禁动作幂等且廉价），或改可观测判据（如「同一回合内」） |
| R6 | 双向罚 × 模糊谓词：做与不做都设违例且触发谓词无可枚举判据 | FAIL | 补判据，或撤销廉价方向的惩罚 |
| R6' | 单向罚 × 模糊谓词 | WARN | 同上，按批处理 |
| R7 | BLOCK 复读 MUST：删掉该 BLOCK 后 MUST 已完整覆盖该违例 | WARN | 删 |
| R8 | 悬空引用：点名的文件、字段、章节、闭集、工具在真源中不存在或未定义 | FAIL | 补真源定义，或改写引用 |
| R9 | 双真源：同一表、清单、字段集或定义在两个文件各维护一份 | FAIL | 撤一侧留指针 |
| R10 | 模糊谓词接硬后果：「写不清 / 复杂 / 风险高」类自评谓词直接驱动 BLOCK 或强制路由 | FAIL | 补 ≤3 条可核对判据，或降硬为软 |
| R11 | 坏例复活靶子：对照中的坏例指名待废除机制、复述坏动作的可执行细节，或引入好例之外的新概念 | FAIL | 按 §1.14 三不改写，或删坏例 |
| R12 | 禁令堆塑形：行为塑形写成连串禁止句，或门禁约束以散文落在标签外 | WARN | 改祈使句；门禁进标签 |

## 3. 变更流程

WHEN: 新增或修改控制规则或模型接口文案，包括源码中的模型可见字符串
ACTOR: 主代理
MUST:

1. 形成 `CHANGE_PLAN`（≤5 行）：改动位置、动机、受影响执行路径、验证方式。
2. 按§1 / §2检查本次修改，复用已有有效证据。仍有具体问题需要独立判断时，围绕该问题选择对应能力；已有证据足以判断时直接收口。测试、审查只覆盖本次修改，报告如实说明实际采用的方法与结果。
3. 修复后只核对新增差异和未关闭 finding，复用其余有效结论。仍有具体问题无法判断时，按第 2 条选择检查方式。
4. 保留原始审查报告，说明 finding 由什么修改和证据关闭，不把原 fail 报告改成 pass。本次修改对应的已确认签字或机器结果按合同取得。
5. 优先复用现有、快速且覆盖改动的检查，不为减少测试条数另造验证工具，也不因尚有可用审查轮次而继续派发。机械校验（如 `cockpit_map.py --lint`）只作事实输入，不作规则质量结论；语义判断不得由脚本、正则、词频或字段计数替代。

OUTPUT: `CHANGE_PLAN`；派审时附审查结论
BLOCK IF: 命中 §2 任一 FAIL 仍落盘。出口：修正后重试；无法修正时收口 `needs_owner` 或交用户裁决。
STATE UPDATE: 普通规则变更不写 `STATUS.md` / `ROADMAP.md`；命中 checkpoint 或 milestone 时按 `ops/policies/state.md`。

## 4. 审查归属

- 规则质量语义审查：`semantic-review-agent / rule-quality-inspection`，判据即本文件 §1 / §2。
- 代码、说明、注释和提示词中的防御性兜底、软化、吞异常，以及编译器、运行时和Pi适配器的拒发必要性：`verify-agent / anti-defensive-inspection`。按§1.7追踪最坏实际副作用，区分任务失败类偏好与真实授权、输入形状、身份信封和资源保护。
- 提示词膨胀、职责重复、受众错配、真源漂移：`verify-agent / prompt-bloat-inspection`。

三类审查只报告 finding、证据和 gate，不修复被审文件。
